How a gRPC call reaches a mongot pod through Envoy

No Gateway API. The load balancer here is a plain Envoy that MongoDB Controllers for Kubernetes deploys itself when a MongoDBSearch declares loadBalancer.managed — a Deployment, a ConfigMap of bootstrap.json / cds.json / lds.json, and nothing else. There is no Gateway, no GRPCRoute and no BackendTLSPolicy in this cluster. Every label below was read from the running objects on CRC 4.22.

What the figure does not claim

  • That round robin balances cost. It balances request counts. A 12-worker load test drove p99 to 16.3 s with an exact 1000/1000/1000 split and zero errors — perfectly even, and still saturated.
  • That the second Envoy is misconfigured. It is ready and healthy. Source hashing at the Route means it only takes traffic when the first one goes away, or when a second distinct client connects.
  • That the MetalLB VIP is unused in general. It is the alternative entry point and it works; this deployment currently points mongotHost at the Route, so the VIP carries nothing right now.
  • Anything about the reverse sync leg's balancing. Each mongot opens its own change stream directly to the replica set. It does not pass through Envoy.
